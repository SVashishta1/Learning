# 3.6 · Churn predictor, end to end: data → pipeline → tuning → API

**What you'll build:** the way ML actually ships at companies. Messy customer data (with missing values) goes into a scikit-learn **Pipeline**. You compare two models with **cross-validated grid search**, check the winner on held-out data, **save** it to disk, and serve it from a **FastAPI** `/predict` endpoint with input validation and tests.
**Like you're 10:** a phone company wants to know which customers are about to leave, so they can call them *before* they go. Your model is the early-warning siren.
**Time:** ~3 h · **Builds on:** [3.5 Model evaluation playground](../05-model-evaluation-playground) and Level 1's APIs ([1.2](../../level-1-apis/02-calculator-api-query-parameters), [1.7](../../level-1-apis/07-dockerize-and-deploy-to-the-cloud)) · **Needs:** nothing extra

## Why this matters
"Churn" means customers leaving. Predicting it is one of the most common ML jobs in telecoms, banks, gyms and software subscriptions, because keeping a customer is much cheaper than finding a new one. More importantly, this project is the full shape of a real ML system: prepare data, compare models fairly, save the winner, and put it behind an API other software can call. This is a strong portfolio piece.

## What you'll learn
- **Pipeline**: preprocessing (fill gaps, scale, encode) and the model saved together, so training and serving can never disagree.
- **Hyperparameter tuning with `GridSearchCV`**: trying settings with cross-validation instead of guessing.
- **Baselines**: always compare a fancy model (gradient boosting) against a simple one (logistic regression).
- **Model artifact**: saving the trained pipeline to a file with `joblib` and loading it in an API.
- **Input validation**: Pydantic rejects bad requests before they reach the model.

## How it works
```
data.py ─► train.py ─────────────────────────────────────────► churn_model.joblib ─► api.py ─► /predict
            make_customers → split → Pipeline(prep + model)                          load once     validate (Pydantic)
                                     GridSearchCV × 2 models                                       → predict_proba
                                     pick best → test once → save                                  → JSON answer
```
1. **`data.py` → `make_customers()`** creates 3,000 fake telecom customers: contract type, months as a customer (`tenure_months`), monthly bill, support calls, internet type and payment method. A **hidden rule** (a logistic formula, like 3.2's model) decides who churned: month-to-month contracts, short tenure, high bills, many support calls and paying by electronic cheque all raise the chance. Then 3% of `monthly_charges` are blanked out (`NaN`), because real data always has holes.
2. **`train.py` splits** off 20% as a test set (`stratify=y` keeps the same churn rate in both parts). That test set is used **once**, at the very end.
3. **`prep` (a `ColumnTransformer`)** treats column types differently:
   - numbers (`NUMERIC`): `SimpleImputer(strategy="median")` fills missing values with the median, then `StandardScaler` scales them;
   - categories (`CATEGORICAL`): `OneHotEncoder` turns `"fiber"` into columns like `internet_fiber=1, internet_dsl=0, internet_none=0`, because models need numbers. `handle_unknown="ignore"` means a category never seen in training won't crash it.
4. **`Pipeline([("prep", prep), ("model", model)])`** chains preprocessing and model into one object. When you call `fit`, the imputer learns the median *from training data only*; when you call `predict` later, it reuses that same median. Doing these steps by hand, separately in training and in the API, is the most common real-world ML bug (**training/serving skew**).
5. **`GridSearchCV`** tries every combination in each model's grid (3 values of `C` for logistic regression; 2 depths × 2 learning rates for gradient boosting) with 5-fold cross-validation, scoring by **AUC** (from 3.5). The `model__C` naming means "the `C` setting of the step called `model`". `n_jobs=-1` uses all CPU cores.
   - **Gradient boosting** (`HistGradientBoostingClassifier`; in industry often XGBoost or LightGBM) builds many small trees, each fixing the previous ones' mistakes. It's usually the king of tabular data, **but here logistic regression wins**. The hidden rule in `data.py` is a logistic formula, so the simple model matches it exactly. Lesson: always compare against a simple baseline before reaching for something fancy.
6. **Final check and save.** The winner's `best_estimator_` (already refitted on all training data) is scored once on the held-out test set. `joblib.dump` saves a small dictionary to `churn_model.joblib` (next to `train.py`, via `MODEL_PATH`): the whole pipeline, the column order, and the model's name.
7. **`api.py`** loads that file **once at startup** into `bundle` (loading per request would be slow). The `Customer` class describes a valid request:
   - `Literal["month-to-month", "one-year", "two-year"]` only accepts those exact strings;
   - `Field(ge=0, le=120)` means "between 0 and 120". FastAPI answers `422 Unprocessable Entity` for anything else, before your code runs.
8. **`predict()`** turns the request into a one-row DataFrame with columns in the training order (`bundle["features"]`), calls `predict_proba`, and returns the probability, a risk label and a suggested action. If no model file exists, it returns `503` with a hint to run `train.py`.
9. **`test_api.py`** trains a model first if `churn_model.joblib` is missing, then uses FastAPI's `TestClient` (a fake browser, no server needed) to check that a risky customer scores above 0.7 and a loyal one below 0.2, and that bad or incomplete input gets a 422.

## If something goes wrong
- **`503: Model not trained yet. Run: python train.py`** → exactly that: run `python train.py` in this folder, then restart uvicorn (the model is loaded at startup).
- **`ERROR: Error loading ASGI app. Could not import module "api"`** → you started uvicorn from the wrong folder. `cd` into the project folder first.
- **`[Errno 48/98] Address already in use`** → another server is on port 8000 (maybe from Level 1). Stop it with `Ctrl+C`, or run `uvicorn api:app --reload --port 8001`.
- **`422 Unprocessable Entity`** → your JSON has a typo, a missing field, or a value outside the allowed range. The response's `detail` says which field.
- **`ModuleNotFoundError` / `RuntimeError: The starlette.testclient module requires the httpx package`** → activate your virtual environment and run `pip install -r requirements.txt`.

   ```python
   @app.post("/predict/batch")

   ```
   FastAPI validates every customer in the list. Try it in `/docs` with `[{...risky...}, {...loyal...}]`: you get `0.992` and `0.007`.
   </details>
2. **Explain the model.** Add a `GET /explain` endpoint that returns how much each feature matters, using `sklearn.inspection.permutation_importance` (it shuffles one column at a time and measures how much the score drops).
   <details><summary>Solution</summary>

   ```python
   @app.get("/explain")
   def explain():
       if bundle is None:
           raise HTTPException(503, "Model not trained yet. Run: python train.py")
       from sklearn.inspection import permutation_importance
       from data import make_customers
       df = make_customers(n=500, seed=99)            # fresh customers the model hasn't seen
       X, y = df[bundle["features"]], df.churned
       result = permutation_importance(bundle["pipeline"], X, y, scoring="roc_auc", n_repeats=5, random_state=0)
       scores = dict(zip(bundle["features"], result.importances_mean.round(3)))
       return dict(sorted(scores.items(), key=lambda kv: -kv[1]))
   ```
   You get roughly `{"contract": 0.201, "tenure_months": 0.072, "monthly_charges": 0.038, ...}`: shuffling the contract column costs the most AUC, so it matters most.
   </details>
3. **Containerise it.** Package the API in Docker using the pattern from [1.7](../../level-1-apis/07-dockerize-and-deploy-to-the-cloud).
   <details><summary>Hint</summary>

   Train first so `churn_model.joblib` exists, then use a `Dockerfile` like:
   ```dockerfile
   FROM python:3.12-slim
   WORKDIR /app
   COPY requirements.txt .
   RUN pip install --no-cache-dir -r requirements.txt
   COPY api.py data.py churn_model.joblib ./
   CMD ["uvicorn", "api:app", "--host", "0.0.0.0", "--port", "8000"]
   ```

   `docker build -t churn-api .` then `docker run -p 8000:8000 churn-api`. Use the same scikit-learn version in the image as you trained with, or loading the model can fail.
   </details>

## Check yourself
1. Why must the imputer and scaler be *inside* the pipeline that gets saved, rather than run separately before training?
2. Why did logistic regression beat gradient boosting here, and what's the general lesson?
3. Why is the test set used only once, after the grid search?
4. What happens if someone sends `"tenure_months": -5` to the API, and why is that better than letting it through?

<details><summary>Answers</summary>

1. So the API applies exactly the same transformations (same median, same scaling, same one-hot columns) as training did. Separate code paths drift apart and silently give wrong predictions (training/serving skew).
2. The hidden rule is linear-logistic, which is exactly the shape of logistic regression. A fancy model can't beat a simple model that already matches the truth. Always try a simple baseline first.
3. If you used it to choose between models or settings, you'd be tuning to it, and its score would no longer be an honest estimate for new data. Cross-validation on the training set does the choosing.
4. Pydantic rejects it (`ge=0`) with a 422 error saying what's wrong. Otherwise the model would happily return a meaningless probability and nobody would notice the bad data.
</details>
